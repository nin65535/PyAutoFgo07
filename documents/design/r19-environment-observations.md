# R19 実環境の表示情報（2026-09-26）

## 計測対象

- OS: Windows、エミュレータ: LDPlayer（ウィンドウタイトル `LDPlayer`、プロセス `dnplayer`）
- ディスプレイ: 2枚。LDPlayerはプライマリ画面上に配置されている。
- 取得方法: Win32の `GetWindowRect`、DWMの拡張フレーム矩形、`GetDpiForWindow`、Windows Formsの画面列挙、およびプロジェクトの `.venv` からの `pyautogui.size()`。

## 計測結果

| 項目 | 値 |
| --- | --- |
| プライマリ画面の物理解像度 | `2560×1600`（`pyautogui.size()`） |
| プライマリ画面のWindows Forms上の論理解像度 | `1707×1067`、原点 `(0, 0)` |
| プライマリ画面の表示倍率 | `150%`（LDPlayerのウィンドウDPI `144`、基準DPI `96`） |
| セカンダリ画面のWindows Forms上の論理解像度 | `1920×1080`、原点 `(2560, 0)` |
| LDPlayerの通常プロセスから見た矩形 | 左上 `(213, 138)`、`1308×743` |
| LDPlayerの物理ピクセル矩形 | 左上 `(319, 207)`、`1962×1115` |
| 新アプリの仮想環境で `pyautogui` を読み込んだ後の `GetWindowRect` | 左上 `(319, 207)`、`1962×1115` |

通常プロセスから見たLDPlayerの矩形は、WindowsのDPI仮想化により約3分の2の値となる。`pyautogui` を読み込んだ新アプリのPythonプロセスではDPI認識が有効になり、旧アプリの基準 `1962×1115` と一致する物理ピクセル座標が返ることを確認した。ウィンドウ左上と旧アプリの相対座標を加算する現在の実装は、この環境では同じ座標系を使う。

## 画面キャプチャと座標対応

- LDPlayerの全体キャプチャは `1962×1115` ピクセルで、ウィンドウの物理ピクセル矩形と一致した。
- 旧設定の攻撃ボタン領域は、ウィンドウ相対 `(1780, 1030, 20, 20)`、デスクトップ絶対 `(2099, 1237, 20, 20)` となった。
- 全体キャプチャから相対領域を切り出した20×20ピクセルと、絶対領域を直接キャプチャした20×20ピクセルは画素単位で一致した。
- 操作コードの画像探索領域は `(2089, 1227, 40, 40)`、予定クリック中心は `(2109, 1247)`。いずれもプライマリ画面の許可範囲内にある。
- 初回計測時のLDPlayerはパーティ編成画面であり、旧アプリの `attack.png` は検出されなかった。
- 診断中、`pyautogui` の初期化前にウィンドウ矩形を取得するとDPI仮想化された論理座標が返ることを確認した。ウィンドウ探索側でもDPI認識を有効化し、初期化順にかかわらず物理ピクセル座標を使うよう修正した。

## 戦闘画面での画像認識

ユーザーが戦闘画面に入った後、同じLDPlayer矩形 `(319, 207, 1962, 1115)` で再計測した。旧アプリの `attack.png`（20×20ピクセル）は、新アプリの探索領域 `(2089, 1227, 40, 40)` 内の `(2099, 1237, 20, 20)` に検出された。検出中心 `(2109, 1247)` は旧座標から算出した予定クリック中心と一致した。検証中は画面取得と画像照合のみを行い、クリック・キー入力は行っていない。

## 単一クリックの安全試験

戦闘画面でLDPlayerの矩形 `1962×1115` と `attack.png` の一致を直前に再確認し、検出中心が予定座標 `(2109, 1247)` と一致した場合だけ `ScreenOperator.click` を1回呼び出した。クリック後、同じ探索領域から攻撃ボタン画像が消え、全体キャプチャでコマンドカード選択画面への遷移を確認した。追加のクリックやキー入力は行っていない。一時キャプチャは確認後に削除した。

## 短いシナリオの段階的確認

`30 カジノ3.json` のwave1先頭命令 `skill(6)` のみを実行した。実行前はwave1の戦闘待機画面で、LDPlayer矩形と攻撃ボタン画像の一致を確認した。3人目の1番目のスキルの予定クリック位置はデスクトップ座標 `(1385, 1112)`。新実装の固定ハンドラーを1命令だけ呼び出し、旧アプリと同じ無指定対象の二重クリックを実行した。ハンドラーは正常終了し、実行後の画面で該当スキルにクールダウン「あと5」が表示された。攻撃ボタン画像は引き続き検出され、wave1の戦闘待機状態を維持している。

ユーザーの実画面での観察により、`skill(6)` の2回目のクリックが意図したスキル演出の早送りとして働いたことも確認した。

次に `skill(7,4)` のみを実行した。直前に同じLDPlayer矩形と攻撃ボタン画像の一致を確認した。スキル7のクリック位置は `(1516, 1112)`、対象4のクリック位置は `(1284, 857)`。新実装の固定ハンドラーは正常終了した。直後の画面では「望月に踊る A」の演出と「NP増加」が表示され、演出終了後はwave1の戦闘待機画面へ戻った。3人目の2番目のスキルにクールダウン「あと6」が表示され、3人目のNPは実行前の50%から100%に変化した。

ユーザーの実画面での観察により、スキル7選択後の効果詳細画面で対象4の位置へのクリックが成功し、同位置での2回目のクリックによる早送りも正常に働いたことを確認した。

続いて `skill(8)` のみを実行した。実行前にwave1の戦闘待機画面と攻撃ボタン画像を再確認した。3人目の3番目のスキルのクリック位置は `(1647, 1112)`。新実装の固定ハンドラーは正常終了し、直後の画面で「月下逍遥／日輪午睡 A」の演出を確認した。演出後はwave1の戦闘待機画面へ戻り、該当スキルにクールダウン「あと6」が表示された。

ユーザーの実画面での観察により、`skill(8)` の発動と2回目のクリックによる演出の早送りが正常に働いたことを確認した。

wave1の最後に `attack(2)` のみを実行した。直前に攻撃ボタン画像の一致を確認した。クリック順は攻撃ボタン `(2109, 1247)`、宝具2 `(1639, 507)`、通常カード0 `(519, 937)`、通常カード1 `(899, 937)`。新実装の固定ハンドラーは正常終了し、直後の画面に宝具が1枚目、通常カードが2・3枚目として選ばれた表示を確認した。攻撃処理後、ゲームはwave2・2ターン目の戦闘待機画面へ進んだ。

wave2では `30 カジノ3.json` の第2グループを `skill(3)` → `skill(4)` → `skill(5)` → `attack(1)` の順に実行した。各命令の前にLDPlayer矩形と攻撃ボタン画像の一致を確認した。

- `skill(3)`: 2人目の1番目のスキルを `(908, 1112)` で操作。ハンドラーが正常終了し、味方全体に回復「3,000」が表示された。
- `skill(4)`: 2人目の2番目のスキルを `(1039, 1112)` で操作。ハンドラーが正常終了し、2人目のNP表示が30%から150%へ変化した。
- `skill(5)`: 2人目の3番目のスキルを `(1170, 1112)` で操作。ハンドラーが正常終了し、戦闘待機画面で2人目の3つのスキルすべてにクールダウンが表示された。
- `attack(1)`: 攻撃ボタン `(2109, 1247)`、宝具1 `(1289, 507)`、通常カード0 `(519, 937)`、通常カード1 `(899, 937)` の順に操作。ハンドラーが正常終了し、宝具が1枚目、通常カードが2・3枚目に選ばれた表示を確認した。攻撃後はwave3・3ターン目の戦闘待機画面へ進んだ。

wave3では `skill(0)` → `skill(1)` → `skill(2)` → `attack(0)` の連続実行を試みた。最初の `skill(0)` は約1.27秒で正常終了し、1人目の1番目のスキルにクールダウン「あと6」、NPは70%から100%となった。しかし直後の `skill(1)` の画像探索で `OperationTimeoutError` が発生し、以降の命令はその試行では実行されなかった。探索1回の制限に画像ポーリング間隔0.1秒を誤用しており、画面取得・照合が0.1秒を超えると、画像が見つかっても失敗することが原因だった。

待機判定を修正し、画像探索1回に操作タイムアウト（既定5秒）、待機全体に戦闘画面タイムアウト（50秒）を適用した。対象テストで修正を確認し、wave3の画面で `skill(0)` のみ使用済みであることを再確認した後、残りの `skill(1)` → `skill(2)` → `attack(0)` を中間の目視確認なしで連続実行した。所要時間はそれぞれ約1.27秒、2.55秒、2.11秒で、残り3命令の合計は約5.92秒だった。宝具0が1枚目、通常カードが2・3枚目に選ばれ、攻撃後は敵0体のRESULT画面へ進んだ。さらにフロントエンドの指令タイムアウトが30秒で、バックエンドの50秒待機より先に切れる不一致が分かったため、操作・通知の余裕を含め90秒へ変更した。

4命令すべてを1回の実行処理で通した検証は、途中停止のため未達成。フロントエンドのシナリオ実行エンジンからの一括実行も未検証。

## 対応範囲

ユーザー指定により、この個人用ツールはこのPCのプライマリ画面での動作を対象とする。セカンダリ画面のDPI測定とLDPlayer移動時の座標検証はR19の対象外とした。画面操作の既定許可範囲もプライマリ画面である。
