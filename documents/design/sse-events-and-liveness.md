# SSEイベント配信と生存監視

## バックエンド

`GET /api/events`は`text/event-stream`で、接続後に生成されたイベントだけを配信する。イベント履歴は保持せず、再送もしない。

- バックエンド起動ごとにUUID v4のセッションIDを生成する。
- 通常イベントにはプロセス内で単調増加するイベントIDを付け、SSEの`id`とJSONの`eventId`を一致させる。
- 指令キューから受付、開始、完了、失敗、取消、実行状態変更を発行する。
- 指令イベントには指令IDを含め、指令ごとに受付、開始、終端の順序を維持する。
- 3秒間イベントがなければ、イベントIDを持たない`heartbeat`を送る。
- `Cache-Control: no-cache`と`X-Accel-Buffering: no`を指定し、途中でのキャッシュやバッファリングを抑止する。

## フロントエンド

標準`EventSource`の自動再接続を使用せず、Fetch APIのストリームを明示的に読み取る。

- 接続開始時を`connecting`、応答ストリーム確立後を`active`として通知する。
- 通常イベントとハートビートのどちらでも最終受信時刻を更新する。
- 最終受信から10秒経過、HTTPエラー、ストリーム終了、読み取りエラー、JSON解析エラーを検出すると即座に`inactive`へ移行する。
- `inactive`へ移行するとストリームを中断し、同じクライアントから再接続しない。
- 通常イベントは`sessionId:eventId`を識別キーとして重複を破棄する。

R11以降の画面は`inactive`状態を受けて、バックエンドを必要とする操作を無効化する。
