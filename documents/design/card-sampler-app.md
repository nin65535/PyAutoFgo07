# カード参照サンプラーアプリ仕様

## 目的と範囲

ステータス画面のスクリーンショットからカード絵柄の参照画像を作り、`scenarios` に登録済みのキャラクターの衣装を追加する。参照画像がまだないキャラクターの最初の衣装も扱う。戦闘画像は参照の切り出し元にせず、登録後の判定確認に使う。`scenarios` に含まれないキャラクターの新規登録、シナリオの編集、評価用正解ラベルの自動生成はこのアプリの対象外とする。

この仕様は**未実装の専用アプリ**に適用する。現行の独立CLIと `schemaVersion: 1` の参照データは [現行の追加手順](../card-appearance-registration.md) と [R24 サンプラー](r24-card-sampler.md)に記す。

## 構成

- プレイヤーとサンプラーは同じリポジトリに置く。フロントエンド、FastAPIアプリ、起動入口、実行プロセスは分ける。サンプラーの専用Chromeは最大化して開き、画面全体を使って画像と候補を比較する。プレイヤーの幅200pxの画面や実行状態に依存させない。
- サンプラー専用のFastAPIで処理要求を受け、サンプラー専用のChromeプロファイルとウィンドウで画面を開く。ポートと認証セッションもプレイヤーから独立させる。プレイヤーの `backend/src/autofgo/main.py` に登録APIを追加して起動しない。
- Pythonの画像切り出し、参照データの検証・保存、ID採番、名前の照合規則は共通モジュールにする。Chrome起動・SSE・ローカル通信の基盤も必要な部分は共有するが、プレイヤーの命令実行や緊急停止をサンプラーへ持ち込まない。
- 専用ChromeプロセスとSSE接続で画面の生存を監視する。Chromeが終了したらサンプラーのバックエンドも終了する。SSEは接続成立後の切断から短い再接続猶予を置き、再接続がなければバックエンドを終了する。ページ再読み込みなどによる瞬間的な切断だけでは終了しない。終了時は受付を止め、進行中の保存を完了またはロールバックしてからプロセスを閉じる。
- 起動時にもう片方のアプリが稼働していれば、後から起動した側に警告を表示する。警告のみで起動は妨げない。通常運用では同時に使わない。
- 参照データの唯一の保存先は `card-data/references/manifest.json` と `card-data/references/images/` とする。元スクリーンショットはサンプラーの作業中だけ保持して破棄し、Gitやアプリの永続領域へコピーしない。元画像サイズと採用した切り出し矩形、分かる場合だけ出典URLを記録する。実行時のカード識別はローカルの承認済み参照だけを読む。

## スクリーンショットの受け取り

- 画面にPNGファイルをドラッグ＆ドロップして読み込めるようにする。ファイル選択ボタンも用意する。ドロップされたファイル名やMIME表示だけを信用せず、画像をデコードして形式・寸法・容量を検証する。
- Chrome画面にフォーカスがある状態で、スクリーンショット画像を `Ctrl+V` などで貼り付けて読み込めるようにする。貼り付けイベントの画像データを第一の入口とし、「クリップボードから読み込む」ボタンを設ける場合はブラウザーの権限要求や拒否を扱う。画像以外のクリップボード内容は登録しない。
- どちらの入口でも同じ画像プレビューと候補生成へ進む。クリップボード由来には元ファイル名がない場合があるため、`sourceId` はシステムが生成する。`sourceUrl` が不明なら省略する。元画像のアプリ内コピーは保存・キャンセル・エラー・終了時に破棄し、後から同じ切り出しを再現できるとは扱わない。
- サンプラー専用FastAPIは画像用の要求サイズ上限を設ける。プレイヤーAPIの現行64KB上限をそのまま適用しない。手元のステータスPNGは約2.6～2.8MBなので、画像の最大バイト数と展開後の画素数を別々に制限する。読み込み失敗や上限超過は理由を画面に示し、参照データへは何も保存しない。

### エミュレータの外枠とゲーム画面

既存の元画像はLDPlayerのウィンドウ全体で `1962×1114` ピクセル、ゲーム画面は `1920×1080` ピクセルである。現行レイアウトではゲーム画面を元画像の `(0,34)` から `(1920,1114)` の範囲として扱う。ゲーム画面だけの `1920×1080` 画像も受け取れるようにする。候補生成はゲーム画面の座標系で行い、保存する `sourceSize` と `source.crop` は入力された元画像の座標系に戻して記録する。

この外枠の切り分けは現行エミュレータUIを前提とする。外枠の形状や寸法が変わった場合の自動追従は将来課題とし、問題が起きてから対応する。想定外の画像寸法やゲーム画面・見出しの検出失敗を黙って既存配置に当てはめず、登録を止めて理由を示す。

## キャラクターと衣装の選択

1. `scenarios/*.json` の `members` を読み、重複を除いてキャラクター候補を表示する。候補の元表記は表示に残す。
2. 名前の照合時は、最初の全角 `＋` 以降を注釈として除き、残った名前の末尾に空白を挟んだ `guest` があれば除く。前後の空白も除く。例: `キャストリア＋NP50` と `キャストリア guest` は `キャストリア` に対応する。`ダ・ヴィンチ（騎）` など、それ以外の部分は自動で削らない。
3. 注釈を除いた名前が `scenarios` にある候補は、参照画像がまだなくても登録可能にする。参照画像がなければ最初の衣装として登録する。キャラクター名の自由入力、`scenarios` にない名前の追加、名前の推測は行わない。候補の読み取りに失敗した場合は理由を示して登録を止める。`????` や `LA` のような既存 `members` 表記は、別キャラ名へ推測で置き換えない。
4. 選択したキャラクターについて、既存衣装へのサンプル追加か新しい衣装の作成を選ぶ。画面にはキャラクター名、衣装ID、既存衣装の参照サムネイルをすべて表示する。参照が複数ある衣装はそのサムネイルも見られるようにする。衣装の同一性は人が確認する。カードの背景色だけで衣装を分けない。最初は1衣装1参照とし、必要が判明した場合に同一衣装のサンプルを増やす。

## IDとファイル名

- `characterId` は全キャラクターで一意の正整数とする。既存参照からの移行時、または `scenarios` にあるキャラクターの最初の参照登録時にシステムが割り振る。同じキャラクターの後続登録ではそのIDを使う。
- `appearanceId` はキャラクターごとに一意の正整数とする。既存衣装ならそのIDを使い、新衣装ならシステムが次の未使用番号を割り振る。参照エントリの `id` とサンプル番号もシステムが生成し、利用者に入力・変更させない。
- 保存するPNGの名前は `<キャラクター名>-<衣装ID>-<サンプル番号>.png` とする。例: `オベロン-4-01.png`。注釈を除いた名前を使う。Windowsで使えない文字を含む場合は意図せず別名で保存せず、理由を示して止める。既存ファイルは上書きしない。
- 採番済みIDと次に割り振る番号を永続化する。削除したIDを再利用せず、manifestの配列順・ファイル名・シナリオの順番から毎回再計算しない。表示名の変更でも数値IDは保つ。ファイル名を変更する場合は参照エントリも同時に更新する。

## スクリーンショットからの候補生成

1. ステータス画面のスクリーンショットを読み、EXIFの向きを反映する。「コマンドカード」の見出しの文字と背景を含む画像パターンを照合して見出し位置を求める。文字の意味を読むOCRは初期方式では使わない。
2. 見出しの下にあるカード列を探し、5枚のカードの位置を示す。利用者が切り出し元のカードを選ぶ。スクロール位置に依存する固定画面座標だけで切り出さない。
3. 切り出しサイズはラジオボタンで約5種類のプリセットから選ぶ。既存参照に使った `105×100` と `110×100` ピクセルを含め、具体的な組み合わせは候補生成の試作で確定する。選択したサイズで、検出した標準位置の1枚と、ゲーム画面のピクセル座標で上下左右・斜めの8方向へそれぞれ5ピクセルずらした8枚、計9枚の断片を並べる。サイズを切り替えたら9枚を再生成する。
4. 利用者が9枚から1枚選ぶと拡大画像と元画像上の位置を示す。座標値の入力やドラッグによる範囲指定は求めない。利用者がキャラクター、衣装、断片の内容を確認した後に保存し、選んだ矩形を `source.crop` に記録する。
5. 撮り直しが必要かは利用者の目視で判断する。サンプラーは候補の見た目だけで自動的に撮り直しを要求しない。見出しやカード位置を検出できない、矩形が画像外に出るなど候補を正しく生成できない場合は保存できない理由を示し、別の画像を受け取れるようにする。

手元の1962×1114のステータス画像6枚で同じ見出し領域を上下に探索したところ、見出し上端は5枚で `y=390`、1枚で `y=431` に最良一致した。既存参照の切り出し上端は見出し上端から約79～90ピクセル下で、採用したカードも1列目と2列目に分かれる。見出し検出はスクロールのずれを追える見込みだが、見出しからの固定オフセットだけで保存画像は確定できない。異なる解像度やゲーム表示での検出精度は未検証である。

## 保存と確認

- 保存前に、候補画像、名前、衣装、出典、ID、ファイル名、既存データとの重複を検証する。PNGとmanifestの更新は、途中で失敗しても片方だけが残らないよう一まとまりで扱う。
- 人が内容を確認した参照だけを `reviewed: true` とする。未確認の候補を実行時の識別器に渡さない。
- 登録後は対象衣装の戦闘画像で名前の判定を確認し、既存画像で別キャラクターへの誤判定が増えていないことも確認する。`card-data/evaluation/manifest.json` の名前・色・衣装正解は別に人が確認し、参照登録から推測して書き込まない。
- プレイヤーは `All` または `WaveN` の再生開始時に参照manifestと参照PNGを読み込み、その再生の間は同じスナップショットを使う。再生中にサンプラーが保存してもその変更を反映せず、次の再生開始時に読み直す。現行プレイヤーはカード判定のたびにmanifestを読むため、専用サンプラーの実装時にこの動作を変更する。

## 既存データの移行

現行 `references/manifest.json` は `schemaVersion: 1` で `characterId` を持たず、`appearanceId` と参照 `id` は文字列である。専用アプリの実装時に、既存のキャラクターと衣装へ数値IDを一度だけ割り振り、参照PNGの改名とmanifest・識別器・検証ツールの対応を同じ変更で行う。旧形式を読みながら一部だけ数値化しない。移行前後で承認済み参照の読み込みと既存戦闘画像の判定結果が保たれることを確認する。
