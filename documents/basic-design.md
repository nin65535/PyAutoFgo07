# autoFgo 基本設計

## 1. 目的

本アプリケーションは、設定ファイルに記述された指令に従い、ゲーム画面の監視とクリックなどの操作を自動的に繰り返すためのツールである。

旧アプリケーション（`C:\2406_autoplay`）は仕様および挙動の調査にのみ使用し、本プロジェクトでは既存コードを直接改修せず、新しいアプリケーションとして実装する。

## 2. システム構成

アプリケーションは、Chrome 上で動作するフロントエンドと、PC 上で動作するバックエンドから構成する。

### フロントエンド

- Chrome
- Vite
- React
- TypeScript

フロントエンドを自動操作全体の制御主体とし、設定ファイルの解釈、実行状況の管理、次に行う操作の判断を担当する。

フロントエンドは Vite を使用して構築する SPA（Single Page Application）とする。画面遷移によるページ全体の再読み込みは行わず、実行中の状態と SSE 接続を維持したまま表示内容を切り替える。

### バックエンド

- Python
- FastAPI
- pyautogui

バックエンドは、フロントエンドから受け取った細かな指令を実行する。画面の取得・監視、クリック、キー入力など、OS と直接やり取りする処理を担当する。

## 3. 責務分担

### フロントエンドの責務

- ユーザーが選択した操作手順JSONの読み込み
- 操作手順JSONの一覧表示とマウスによる選択
- 設定ファイルの構文および内容の検証
- 設定ファイルに記述された指令の解釈
- 自動操作シナリオの進行状況と状態の管理
- 実行開始、一時停止、再開、停止の制御
- バックエンド API への画面監視や画面操作の要求
- SSE イベントの受信と画面表示の更新
- バックエンドからの通知に基づく次の指令の決定
- エラー、タイムアウト、実行履歴の表示

### バックエンドの責務

- FastAPI による API の提供
- アプリケーション管理下にある操作手順JSONの列挙と内容の提供
- pyautogui によるスクリーンショット取得
- 指定領域や指定画像の監視
- マウス移動およびクリック
- キー入力などのPC操作
- 指令の直列実行と多重操作の防止
- 実行結果、状態変化、エラーの通知
- SSE 接続の管理
- アプリケーション専用プロファイルを指定した Chrome の起動
- Chrome と SSE 接続の生存監視
- 緊急停止と安全制御
- Chrome 終了時のバックエンド終了処理

バックエンドは設定ファイル全体やシナリオ進行を原則として解釈しない。フロントエンドから渡された、単一の目的を持つ細粒度の指令を実行する。

## 4. 基本的な処理フロー

```text
設定ファイル
    ↓ 読み込み・検証・解釈
React / TypeScript
    ↓ REST APIによる細かな指令
FastAPI
    ↓
pyautoguiによる画面監視・画面操作
    ↓ 実行結果・状態変化
FastAPI
    ↓ SSE
React / TypeScript
    ↓ 状態更新・次の指令を判断
処理を繰り返す
```

1. ユーザーが Python 側のプログラムを起動する。
2. バックエンドが FastAPI の待ち受けを開始する。
3. バックエンドが専用プロファイルを指定して Chrome を起動し、フロントエンドの URL を開く。
4. フロントエンドがバックエンドとの SSE 接続を確立する。
5. ユーザーが Chrome 上の一覧から操作手順JSONをマウスで選択する。
6. フロントエンドが設定ファイルを読み込み、内容を検証する。
7. フロントエンドが最初に実行する指令を決定する。
8. フロントエンドが REST API を通じてバックエンドへ指令を送る。
9. バックエンドが pyautogui を使って監視または操作を実行する。
10. バックエンドが実行結果や更新要求を SSE でフロントエンドへ通知する。
11. フロントエンドが状態を更新し、次の指令を決定する。
12. 停止条件、完了条件、またはエラー条件を満たすまで繰り返す。

## 5. アプリケーションの起動と終了

### 起動

本アプリケーションは Python 側のプログラムを起点として起動する。ユーザーが Chrome を別途起動して URL を入力する操作は、通常の起動手順には含めない。

1. Python プログラムが FastAPI を起動する。
2. API が接続可能になったことを確認する。
3. アプリケーション専用のユーザーデータディレクトリを指定して Chrome を起動する。
4. Chrome で本アプリケーションのフロントエンドを開く。
5. フロントエンドが SSE 接続を開始する。
6. バックエンドが接続確立を確認した後、アプリケーションを利用可能な状態にする。

起動する Chrome には、普段使用する Chrome と分離した本アプリケーション専用プロファイルを用いる。専用プロファイルの保存先はアプリケーションのデータ保存場所として明示的に管理し、通常利用している Chrome の履歴、Cookie、拡張機能、ログイン状態などに依存しない構成とする。

Chrome のウィンドウは画面左側の細い領域に配置し、ゲームが使用する画面領域をできる限り占有しないサイズで起動する。ウィンドウの位置と大きさは、画面解像度および利用環境に応じて調整できるようにする。

同じ専用プロファイルを使用するアプリケーションがすでに起動している場合は、別インスタンスを起動せずエラーとして扱う。

### Chrome の生存確認

バックエンドは SSE ストリームに一定間隔でハートビートイベントを送信する。Chrome 上のフロントエンドが終了して SSE 接続が切断されたことを、バックエンドが検知できるようにする。

SSE はバックエンドからフロントエンドへの一方向通信であるため、Chrome から応答を返す方式ではない。バックエンドがハートビートの送信失敗または SSE 接続の切断を検知することで、Chrome の生存状態を判定する。

OS やネットワーク処理の都合で SSE の切断検知に時間がかかる可能性があるため、バックエンドが起動した Chrome プロセスの終了状態も補助的に監視する。終了判定は、SSE 接続と専用 Chrome プロセスの状態を組み合わせて行う。

### Chrome 終了時の緊急停止

一度 SSE 通信が確立した後に、対象となる Chrome ウィンドウが閉じられた場合は、通常停止ではなく緊急停止として扱う。

緊急停止では、次の順序で処理する。

1. 新しい API 指令の受付を停止する。
2. 実行中の画面監視、マウス操作、キー入力を可能な限り即座に中断する。
3. キューに残っている未実行の指令をすべて破棄する。
4. 入力中のキーやマウスボタンがある場合は解放する。
5. 緊急停止の理由と破棄した指令をログへ記録する。
6. FastAPI と関連するバックグラウンド処理を停止する。
7. Python プロセスを終了する。

Chrome 終了後は、キューに処理が残っていても完了を待たない。安全な入力解除とログ記録に必要な最小限の終了処理だけを行い、バックエンドを終了する。

## 6. 通信方式

### REST API

フロントエンドからバックエンドへの指令には HTTP の REST API を使用する。

想定する指令の例：

- スクリーンショットを取得する
- 指定領域を監視する
- 指定画像が表示されているか判定する
- 指定座標をクリックする
- 指定キーを入力する
- 実行中の処理を中止する
- バックエンドの状態を取得する
- 利用可能な操作手順JSONの一覧を取得する
- 選択した操作手順JSONの内容を取得する

API の具体的なエンドポイントとリクエスト形式は、設定ファイルの仕様と操作要件を整理した後に定義する。

### Server-Sent Events（SSE）

バックエンドからフロントエンドへの非同期通知には SSE を使用する。

想定するイベントの例：

- 指令の受付
- 指令の開始
- 指令の完了
- 監視対象の検出
- 監視のタイムアウト
- 実行状態の変更
- 警告またはエラー
- フロントエンドへの状態更新要求
- Chrome の生存確認用ハートビート

各イベントには、イベント種別、指令を識別する ID、発生日時、結果データを含める。

## 7. 状態管理

自動操作全体の状態は、フロントエンドで一元管理する。

基本状態として、以下を想定する。

- `idle`: 未実行
- `running`: 実行中
- `paused`: 一時停止中
- `stopping`: 停止処理中
- `completed`: 正常終了
- `error`: エラー終了
- `emergency_stopping`: Chrome 終了などによる緊急停止処理中

フロントエンドは各 API 指令に一意な ID を付与し、SSE で返されるイベントと対応付ける。同一イベントの再受信や通信の再接続が発生しても、同じ操作を誤って二重実行しない設計とする。

## 8. 操作手順ファイル

ゲームの操作手順は旧実装と同様に JSON ファイルとして保存する。バックエンドが JSON ファイルを読み込んでフロントエンドへ提供し、フロントエンドが内容を検証・解釈した後、記述された手順に従って実行状態と次の指令を管理する。

操作手順JSONは、アプリケーションが管理する所定のフォルダへ保存する。バックエンドはこのフォルダから利用可能なJSONを列挙し、フロントエンドへ一覧と選択されたファイルの内容を提供する。このファイルI/Oをバックエンドへ集約する方針を、新アプリでも踏襲する。

バックエンドはファイルの安全な読み込みとJSONとしての構文確認までを担当する。操作手順のスキーマ検証、命令の意味解釈、シナリオ進行はフロントエンドが担当する。

操作手順ファイルについて、以下を基本方針とする。

- 文字コードは UTF-8 とする
- バックエンドでJSONとして解析できないファイルはフロントエンドへ操作手順として提供しない
- 必須項目、値の型、値の範囲を TypeScript 側で検証する
- 検証エラーは、対象項目と理由をフロントエンドに表示する
- 読み込んだ原文を直接変更せず、検証済みの内部表現へ変換してから実行する
- ファイル内に任意の JavaScript、Python、シェルコマンドを記述・実行できない仕様とする
- 将来の形式変更を識別できるよう、スキーマバージョンの導入を検討する
- ファイル名や相対パスはバックエンドで検証し、管理フォルダ外のファイルを取得できないようにする

### 操作手順API

操作手順の取得には、少なくとも次のAPIを用意する。

```http
GET /api/scenarios
GET /api/scenarios/{scenario_id}
```

- 一覧APIは、選択画面に必要なID、表示名、更新日時などを返す
- 内容取得APIは、一覧APIで得たIDに対応するJSONの内容を返す
- クライアントから絶対パスを受け取らない
- IDから解決したファイルが管理フォルダ内にあることを確認する
- `.json` 以外のファイルは操作手順として扱わない
- 存在しない、読み取れない、または不正なJSONの場合は、機械判定可能なエラーレスポンスを返す

旧実装の操作手順ファイルは、メンバー名を保持する `members: string[]` と、複数の操作文字列をグループ化した `commands: string[][]` を持つ。操作文字列には `skill(0)` や `attack(0,1,2)` などの形式が使われていた。バックエンドは文字列を分解し、`getattr(Player, 関数名)` によって Python のメソッドへ直接対応付けていた。

手書き時の記述量を増やさないため、`skill(0)` などの簡潔な文字列表現と旧JSONの基本構造は維持する。ただし、文字列からPythonの関数を動的に呼び出す旧実装は踏襲しない。

旧アプリの操作手順JSONを調査した時点では、20ファイル、313命令が存在し、使用されている命令は `skill`、`master_skill`、`attack`、`swap` の4種類である。これらを新アプリが対応する限定的な命令記法として定義する。

### 安全な文字列コマンド

操作手順JSONでは、旧形式と同じ簡潔な命令を記述できる。

```json
{
  "members": ["メンバーA", "メンバーB"],
  "commands": [
    ["skill(0)", "skill(5,2)", "attack(0,1)"]
  ]
}
```

この文字列はPython式ではなく、本アプリ専用の限定的な命令記法として扱う。TypeScript側に命令ごとの厳格なパーサーを実装し、文字列全体が定義済みの文法へ完全一致した場合だけ受け付ける。

パーサーは次の処理だけを行う。

- 命令名を `skill`、`master_skill`、`attack`、`swap` などの許可リストと照合する
- 命令ごとに引数の個数を検証する
- 引数を符号なし整数として読み取る
- 引数の値域と組み合わせを検証する
- 未知の命令、余分な文字、式、文字列、コメントなどを拒否する
- エラー時はJSON内の命令位置と理由を表示する

例えば `skill(5,2)` は、フロントエンド内部で次の型付きデータへ変換する。

```json
{
  "type": "use_skill",
  "skill": 5,
  "target": 2
}
```

この型付きデータだけを操作APIへ送る。バックエンドはPydanticなどで再検証し、命令種別をソースコード上の固定ハンドラーへ対応付ける。元の文字列コマンドをPythonへ送信したり、Python側で評価したりしない。

フロントエンドとバックエンドのどちらでも、次の仕組みは使用しない。

- `eval` または `exec`
- リクエスト値を使用した `getattr`
- 動的なモジュールまたは関数のインポート
- 任意の Python コード、JavaScript、シェルコマンドの実行
- JSONに記述された任意のファイルパスや実行ファイルの起動

バックエンドの命令ディスパッチは、例えば `{"click": handle_click, "capture": handle_capture}` のように、ソースコード上で定義した固定の対応表を使用する。JSONやAPI入力から、呼び出すPythonシンボル名を決定しない。

この方式により、旧JSON資産との互換性と手書きの簡潔さを保ちながら、Python内部への動的な呼び出しを排除する。一括変換機能は必須としない。

### 操作手順の選択方法

ゲーム中でもマウスだけで操作できることを必須要件とする。通常の実行操作では、次の入力方法を使用しない。

- OS のファイル選択ダイアログ
- ファイルのドラッグ＆ドロップ
- ファイルパスのテキスト入力
- 操作手順名を選ぶためのキーボード入力

フロントエンドは、バックエンドから取得したJSONの一覧を、クリックまたはタップ可能な項目として表示する。ユーザーは一覧から対象を選択し、内容の概要を確認して、開始ボタンを押すだけで実行できるものとする。

操作手順の追加、削除、編集など、ゲーム実行中には不要な管理操作は通常の実行画面から分離する。管理操作にOSのファイル選択などが必要になった場合でも、通常の実行フローには含めない。

## 9. フロントエンド画面設計

### 基本方針

フロントエンドは、画面左側の細い領域だけで使用する縦長の SPA とする。画面の大部分はゲーム表示のために確保し、操作パネルがゲーム画面へ重ならない配置を基本とする。

- 狭い横幅でも操作できる1カラム構成とする
- 通常の実行操作をマウスだけで完結できるようにする
- 操作手順はファイル一覧から大きなクリック領域で選択できるようにする
- 小さすぎるボタンや、マウスオーバーしなければ利用できない操作を避ける
- 横方向へのスクロールは発生させない
- 情報は重要度順に上から配置する
- 実行状態、停止操作、エラーを常に確認できるようにする
- 詳細設定やログは折りたたみ表示などを用いて必要時だけ展開する
- 長い設定名やメッセージは省略表示し、必要に応じて全文を確認できるようにする
- 画面の高さを超える内容だけを縦方向にスクロール可能とする
- ウィンドウ幅が変化してもレイアウトが破綻しないようにする

### 画面上の優先順位

上から順に、概ね以下の要素を配置する。

1. バックエンドおよび SSE の接続状態
2. 現在の実行状態と実行中の指令
3. 緊急停止ボタン
4. 開始、一時停止、再開、通常停止の操作
5. 操作手順JSONの一覧、選択内容、検証結果
6. 直近の実行結果、警告、エラー
7. 詳細な実行履歴とログ

緊急停止ボタンは、スクロール位置にかかわらず操作できるように固定表示を検討する。誤操作を防ぎつつ、緊急時には最小限の操作で停止できる形とする。

### ウィンドウ配置

Python 側から Chrome を起動する際に、起動オプションを使ってウィンドウを画面左端へ配置する。ウィンドウの具体的な横幅、最小幅、位置の保存方法、および複数ディスプレイへの対応は、実際のゲーム画面と操作性を確認して決定する。

### 旧実装の起動設定

旧実装の `python/front/front.py` では Selenium WebDriver を使用し、次の設定で Chrome を起動している。

| 項目 | 旧実装の設定 |
| --- | --- |
| 表示モード | `--app=http://localhost:8001` |
| ウィンドウ位置 | 左上 `(0, 0)` |
| ウィンドウサイズ | 幅 `200` × 高さ `1000` ピクセル |
| ユーザーデータ | `C:\tmp\User Data` |
| プロファイル | `Profile1` |
| 自動操作表示 | `enable-automation` スイッチを除外 |

新実装では Selenium の採用を前提とせず、旧実装の左配置と縦長サイズを初期設計の参考にする。専用プロファイルの保存先は一時ディレクトリではなく、新アプリケーション用の永続データ保存先として改めて定義する。

## 10. 安全性に関する基本方針

ゲーム操作を自動化する性質上、意図しないマウス・キーボード操作を防ぐ仕組みを設ける。

- 緊急停止手段を常に利用可能にする
- Chrome 終了時は未実行のキューを破棄し、実行中の操作も中断する
- 緊急停止を通常の指令処理より常に優先する
- バックエンドで同時に実行する操作を原則1件に制限する
- 各監視処理および操作にタイムアウトを設定する
- 座標、画面領域、入力値をバックエンドでも検証する
- フロントエンドとの接続断を検知した場合の停止方針を定める
- 実行中の指令と結果をログに記録する
- FastAPI は原則としてローカルホストからのみ接続可能にする
- 任意の Python コードやシェルコマンドを設定ファイルから実行できない構造にする
- APIで受け付ける命令種別を固定の許可リストに限定する
- 命令ごとにバックエンドでも型、値域、座標範囲を検証する
- リクエスト値から Python の関数やメソッドを動的に探索しない
- 専用Chrome以外のWebページから操作APIを呼び出せないよう、接続元とセッショントークンを検証する

## 11. 今後定義する事項

- 操作手順JSONのスキーマとバージョン管理方法
- 限定的な文字列コマンドの正式な文法、許可する命令、各引数の値域
